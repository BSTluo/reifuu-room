## 1. 游戏概述

### 1.1 游戏定位
- **游戏类型**：2.5D 多人在线聊天游戏（Social Sandbox / MMO-lite）
- **核心体验**：玩家在一张像素风大陆地图上自由行走，采集资源、建造属于自己的"聊天室"，多个聊天室聚集形成城镇，通过传送门在城镇间穿梭；聊天室内可以文字聊天、一起听歌看视频、摆放装饰——把"聊天"这件事，变成一个可以经营、可以社交、可以逛的虚拟空间。
- **目标玩家**：喜欢轻社交、轻建造、二次元像素美术的年轻玩家群体，类似"动物森友会 + 开放世界聊天室"的玩法组合。

### 1.2 美术风格
- 二次元像素中世纪风格（Pixel Art / 16-bit 风格，参考《符文工房》《牧场物语》类像素游戏的中世纪村庄质感，角色为二次元Q版人形）。
- 场景基调：中世纪村落、田野、矿脉、森林，四大洲各有主题化的美术差异（见 2.2）。
- 分辨率建议：角色 32x32 或 48x48 tile 基准，贴图统一像素密度，避免 2.5D 视差层与像素风格穿帮。

### 1.3 技术栈
- **客户端**：Vue 3（UI 层：登录、面板、菜单）+ Phaser 3（游戏世界渲染：地图、角色、动画）
- **服务器**：Node.js（TypeScript），WebSocket 实时通信 + REST API
- 当前仓库已有 `client/reifuu-chat`（Vue + Vite 脚手架，待接入 Phaser）与 `server`（空的 Node.js/TS 骨架），本设计文档即在此基础上规划落地。

## 2. 核心系统设计

### 2.1 用户系统

**功能范围**
- 注册：邮箱/用户名 + 密码，服务端 bcrypt 加密存储，基础格式校验。
- 登录：账号密码登录，返回 JWT（access token + refresh token），WebSocket 连接时用 access token 鉴权。
- 角色创建：首次登录进入创角流程——选择性别/发型/肤色/初始服装（像素形象由预设部件拼装，避免自由绘图带来的美术成本），**选择出生方式与出生点**。

**出生点选择机制（无邀请新玩家）**
- 在创角流程的最后一步，玩家需选择出生方式（两种互斥选项）：
  1. **随机无主地块**：系统从四大洲中随机挑选一个完全未被任何玩家占领（`ownerId = NULL`）的空地区块作为出生点。
     - 优势：完全独享的起始区域，资源不与他人竞争，适合喜欢独立发展的玩家。
     - 劣势：周边可能较为荒凉，缺少社交氛围（除非主动探索遇见其他玩家）。
  2. **随机公开地块**：系统从已有玩家拥有但设置为"公开"（`isPublic = true`）的地块中随机分配一个作为出生点。
     - 优势：出生点周边可能已有其他玩家的聊天室/城镇雏形，更容易遇见其他玩家并快速融入社交。
     - 劣势：资源可能已部分被采集，需要稍远一些的探索才能找到未被开发的资源区块。
- **匹配算法**：
  - 无主地块池：服务器维护一个"候选无主地块列表"（定期扫描 MapChunk 表，筛选 `ownerId IS NULL AND type IN (空地, 资源)`，缓存到 Redis），从中随机抽取。
  - 公开地块池：维护"公开地块列表"（`ownerId IS NOT NULL AND isPublic = true`），按人口密度/活跃度排序（优先推荐有一定人气但未过度拥挤的区块），随机抽取前 N 个中的一个（避免所有新手涌入同一公开地块）。
- **邀请码出生**（Phase 3 后扩展）：若玩家通过好友邀请码注册，可直接出生到邀请者所在地块（需邀请者地块为公开或邀请者手动授权），跳过上述随机流程。

**流程**
1. 注册 → 邮箱校验（可选，MVP 阶段可跳过）→ 创角（外观选择）→ **出生方式选择（无主地块 / 公开地块）** → 服务器分配出生点 → 进入游戏世界。
2. 登录 → 校验 token → 拉取角色数据、所在区块数据 → WebSocket 建立连接 → 进入游戏世界。

**安全要点**
- 密码存储必须加盐哈希（bcrypt/argon2），不可明文/仅MD5。
- JWT 需设置合理过期时间，refresh token 走 httpOnly cookie 或安全存储，避免 XSS 窃取。
- 所有登录态接口需鉴权中间件校验，WebSocket 连接建立时校验 token 而非信任客户端上报的用户ID。

### 2.2 地图系统

**世界结构**
- 整个游戏世界是一整块大陆，划分为 **东、南、西、北四大洲**，每个大洲有独立的主题美术风格（例如：东-竹林渔村、南-草原农庄、西-矿山丘陵、北-雪原城堡），降低美术复用成本的同时保留探索新鲜感。
- 每个大洲内部通过"区块（Chunk）"网格化管理，区块是地图加载、资源刷新、玩家可视范围的最小单位。

**区块系统**
- 区块尺寸建议：32x32 tile（与 Phaser Tilemap 天然契合），每个大洲由 N x N 个区块拼接组成。
- 区块类型（互斥，一个区块对应一种基础类型，区块内可叠加少量装饰物）：
  | 区块类型 | 说明 |
  |---|---|
  | 资源区块 | 分布木头/石头/矿物等采集点，周期性刷新 |
  | 景观区块 | 纯装饰性地形（河流、花田、遗迹），不可采集不可建造，用于路线引导和氛围 |
  | 空地区块 | 可建造区块，玩家消耗资源在此建造聊天室 |
  | 聊天室区块 | 已建成聊天室所在区块，多个聊天室区块相邻聚集即形成城镇 |
  | 海洋区块 | 大洲间分隔区域，需船只或飞行器穿越（见 2.8 交通工具系统） |
- 区块状态需持久化在服务器（谁建造了什么、资源剩余量、刷新倒计时、**所有权归属**），客户端仅按可视范围向服务器请求区块数据（避免一次性加载整张大陆）。

**地块所有权系统**
- **所有权获得机制**：
  - 玩家在某个空地/资源区块采集足够资源并建造聊天室后，该区块的所有权（`ownerId`）自动归属该玩家。
  - 建造聊天室是获得所有权的唯一途径（采集资源但不建房不获得所有权，避免玩家通过单纯采集圈地）。
  - 所有权获得后，区块类型从"空地"变为"聊天室区块"，但所有权记录保留（即使聊天室未来被拆除，所有权仍归原主，除非主动转让/放弃）。
- **个人地块上限**：
  - 每个玩家拥有的地块数量有上限，**默认 10 块**（具体数值 Phase 2 根据地图规模与经济平衡调优，可设为 5-15 块区间）。
  - 达到上限后，玩家需先"放弃"某个已拥有的地块（将 `ownerId` 置空，区块重新变为无主状态），才能在新区块建造。
  - 放弃地块时，该地块上的聊天室将被拆除（资源按一定比例返还，如 50%-80%），或转为"废弃聊天室"（保留建筑但无功能，占用区块但不再消耗维护成本，Phase 5 后考虑）。
- **地块公开设置**：
  - 地块默认状态：**不公开**（`isPublic = false`），即只有拥有者及其邀请的好友/团队成员可以进入该地块上的聊天室。
  - 拥有者可在聊天室设置面板中切换"地块公开状态"：
    - 公开（`isPublic = true`）：任何玩家均可发现并进入该地块，该地块会出现在"随机公开地块"出生点池中，提升人气与社交机会。
    - 不公开（`isPublic = false`）：外来玩家无法随机出生到此地块，需通过传送门/好友传送/邀请码等方式才能到达。
  - 公开地块的拥有者仍保留管理权限（踢人/设置房间权限/关闭公开状态）。
- **团队共享所有权**（见 2.9 团队系统）：
  - 加入团队后，个人地块上限提升为团队共享上限（2 人团队 15 块，3 人团队 20 块，依此类推）。
  - 团队成员可以在团队拥有的任一地块上建造（消耗各自资源或团队共享资源池，Phase 3 需明确资源归属机制）。

**资源类型**
- 木头（森林/景观区块周边低频刷新，建造消耗量大）
- 石头（丘陵/山地区块，建造聊天室地基必需）
- 矿物（矿山区块，稀有度较高，用于高级建造/装饰解锁）
- 资源节点采集后进入冷却重生（如 5-30 分钟不等，具体数值待数值策划迭代），避免资源枯竭导致地图空洞。

### 2.3 游戏玩法

**资源采集机制**
- 玩家靠近资源节点，触发交互提示，按键采集；采集有动作时长（如 1-2 秒），期间可被打断（移动/受击，若未来加PVP）。
- 采集成功获得对应资源，进入玩家背包（背包有容量上限，MVP 可设为格子制）。
- 服务器权威校验：采集请求必须校验玩家与资源节点的实际距离、节点是否处于冷却，防止作弊/瞬移采集。

**建造系统**
- 玩家在"空地区块"发起建造，选择聊天室外观模板（不同模板消耗不同资源组合，例如：木屋消耗木头为主，石屋消耗石头+矿物）。
- 建造过程：选择模板 → 校验资源是否足够并扣除 → 服务器生成聊天室实体（含唯一ID、归属者、初始权限）→ 区块类型从"空地"变为"聊天室"。
- 聊天室可升级/翻新（消耗资源更换外观或扩大房间容量），作为后续资源消耗的长期目标。

**城镇系统**
- 当同一区域内聊天室区块的数量/密度达到阈值（例如：3x3 范围内 ≥5 个聊天室），系统自动识别为"城镇"，或由玩家发起"建镇"申请（消耗额外资源，更符合玩家自主感）。
- 城镇拥有名称（玩家自定义/投票）、城镇等级（随聊天室数量/人气增长解锁装饰、传送权限等）。
- 城镇是传送门系统的"锚点"，也是社交热点的自然承载体。

**传送门系统**
- 每个已形成的城镇拥有一个传送门，玩家可通过传送门 UI 选择已解锁的目标城镇进行传送。
- 解锁条件建议：玩家需实际到访过该城镇一次，才能加入传送列表（鼓励探索而非直接列表选传）。
- 传送可设置冷却时间或少量资源/货币消耗，避免过度削弱地图移动的探索价值。

### 2.4 社交功能

**聊天室功能**
- 文字聊天：房间内广播消息，服务器转发给房间内所有在线成员，历史消息可做短期缓存（如最近100条）。
- 一起听歌：房主/成员上传或选择歌曲（URL 或预置曲库），服务器广播播放状态（曲目、进度、播放/暂停），客户端本地同步播放进度，做基础的时钟对齐（非强实时同步，容忍小误差）。
- 一起看视频：同上机制，同步视频源与播放进度；需注意版权来源，MVP 建议仅支持指定平台的嵌入播放或站内合规资源。
- 房间装饰：房间内可摆放家具类装饰物（消耗资源/货币购买解锁），装饰数据持久化在聊天室实体上，支持简单的网格摆放系统。

**多人互动机制**
- 房间权限分级：房主（建造者，完全权限）、成员（可发言/使用听歌看视频/受限装饰权限）、访客（仅可发言，无编辑权限）。
- 基础互动：表情/动作、点赞（可选）、好友关系（MVP 可选，先做房间维度社交，好友系统作为二期）。

### 2.5 房间插件与扩展系统（可扩展性架构）

**设计目标**：为聊天室提供可扩展的插件机制，允许社区开发者通过标准化SDK开发"房间玩法插件"（如多人斗地主、狼人杀、你画我猜等桌游类、派对游戏类插件），由插件市场分发，玩家在房间内"安装"插件后即可使用，大幅提升房间玩法的多样性与长线留存。

**核心概念**
- **房间插件（RoomPlugin）**：独立打包的扩展包，包含前端UI（Vue组件/Phaser场景片段）、游戏逻辑（客户端脚本+服务端逻辑可选）、资源（图集/音效）、元数据（manifest.json：插件名称/版本/作者/依赖的SDK版本等）。
- **插件市场（Plugin Marketplace）**：官方平台，展示社区插件列表，支持搜索/下载/评分/更新；插件审核机制确保安全性与质量。
- **房间道具（RoomItem）**：插件的"入口消耗品"，玩家在房间内"使用"道具（如"斗地主桌"）即激活对应插件，多人同时进入插件会话。

**插件生命周期**
1. **开发阶段**：开发者基于 SDK（见下文"SDK设计"）本地开发调试插件，打包生成符合规范的插件包（.rpkg 或 .zip）。
2. **上架审核**：开发者提交插件包到插件市场后台，平台进行安全扫描（沙箱执行检测恶意代码、敏感API调用）与内容审核，通过后上架。
3. **安装使用**：玩家在房间内打开插件市场UI，浏览并安装插件到"房间插件库"（每个房间有独立的已安装插件列表，或全局账号级安装后房间内激活）。
4. **激活/卸载**：房主/成员使用"房间道具"激活插件，进入插件会话（插件前端UI叠加在房间内，插件逻辑接管部分交互）；退出插件会话后回到普通聊天室；房主可随时卸载插件。

**架构扩展点（Phase 0~Phase 2 即需预留）**
- **前端扩展点**：
  - `RoomScene` 或 `RoomView` 内预留"插件容器槽位"（Vue动态组件插槽 + Phaser Container），插件UI以"子场景"或"浮层组件"形式注入。
  - EventBus 增加插件专用事件命名空间（如 `plugin:*`），插件通过 SDK 向 EventBus 发送/订阅事件，与房间核心逻辑解耦。
- **后端扩展点**：
  - RoomService 增加 `PluginSessionManager`，维护每个插件会话的状态（参与者列表、插件内数据）。
  - Socket.io 房间按"chatroom_id:plugin_id"二级命名空间划分，插件消息不污染房间主聊天流。
  - 插件可选择"纯客户端逻辑"（如简单的投票游戏，服务器仅转发消息）或"服务端权威逻辑"（如斗地主，服务端校验出牌合法性），后者需要开发者上传服务端脚本（Node.js 模块），在沙箱内执行（VM2 或独立Worker进程）。
- **数据模型扩展**（Phase 2 即需落库表结构预留）：
  - `Plugin`：`id, name, version, author, manifest(JSON), packageUrl, status(审核中/已上架/下架), createdAt`
  - `RoomPlugin`：`id, roomId, pluginId, installedAt, config(JSON)`
  - `PluginSession`：`id, roomId, pluginId, participants(characterId[]), state(JSON), startedAt, endedAt`

**SDK设计（待Phase 4后期或Phase 5补齐，Phase 2需定义接口契约）**

SDK核心模块（`@reifuu-chat/plugin-sdk`，npm包形式分发）：

1. **RoomAPI**（房间能力调用）
   - `room.sendMessage(text)`：向房间主聊天发送消息（需权限）
   - `room.getMembers()`：获取房间当前在线成员列表
   - `room.broadcast(eventName, payload)`：向房间内所有成员广播插件自定义事件
   - `room.setState(key, value)`：持久化插件会话内的KV数据（存储在 PluginSession.state）

2. **PlayerAPI**（玩家信息查询，只读）
   - `player.getId()`：当前玩家的 characterId
   - `player.getNickname()`：玩家昵称
   - `player.getAvatar()`：玩家像素头像（用于插件内展示）

3. **UIAPI**（插件UI生命周期）
   - `ui.mount(component)`：挂载插件的 Vue 根组件到房间插件容器
   - `ui.unmount()`：插件会话结束时卸载UI
   - `ui.showToast(message)`：弹出提示（调用房间全局Toast组件）

4. **NetworkAPI**（插件专用通信，封装Socket.io）
   - `network.emit(eventName, data)`：向服务器发送插件事件（自动带上 pluginId/sessionId）
   - `network.on(eventName, callback)`：监听服务器广播的插件事件
   - 服务端 SDK（`@reifuu-chat/plugin-sdk-server`）提供对应的 `session.broadcast()` / `session.emit(characterId, eventName, data)` 方法

5. **沙箱约束**
   - 插件代码运行在受限环境：前端禁止访问 `window.localStorage`（避免跨插件数据污染）、禁止直接操作 DOM（只能通过 Vue 组件声明式渲染）、禁止发起未经 SDK 封装的网络请求（防止数据外泄）。
   - 服务端插件脚本在 VM 沙箱或独立进程内执行，禁止 `require('fs')`/`require('child_process')` 等危险模块，只能调用 SDK 提供的白名单API。

**插件市场UI（Phase 5 或独立迭代）**
- 房间内新增"插件市场"按钮，打开弹窗UI（Vue Modal）。
- 列表展示插件卡片（名称/图标/简介/评分/安装量），支持搜索/分类筛选。
- 点击"安装"后从服务器下载插件包（前端资源CDN + manifest元数据），本地缓存并注册到房间插件库。
- 房间内"背包/道具栏"新增"使用插件"入口，选择已安装插件即可激活。

**安全与审核机制**
- 插件包签名校验：上传时计算哈希并签名，客户端安装时校验，防止插件被篡改。
- 代码静态扫描：检测明文硬编码的敏感URL、eval/Function动态执行、原型链污染等风险模式。
- 运行时监控：插件会话内异常（崩溃/超时/内存泄漏）自动上报，频繁异常的插件降权或下架。
- 用户举报机制：玩家可举报恶意插件（刷屏/诱导充值/违规内容），人工复审后处理。

### 2.6 视野与探索系统

**设计目标**：引入迷雾战争（Fog of War）机制，玩家初始只能看见有限区块范围，通过移动探索逐步揭开地图，增强探索感与未知的期待感。

**核心机制**
- **初始视野范围**：玩家首次进入游戏时，仅能看见当前所在区块及周围 **5x5 区块**（共25个区块，即以玩家为中心的小范围区域）的地图内容（地形/资源节点/聊天室外观）。
- **探索逻辑**：
  - 玩家角色移动进入新区块时，该区块及其相邻的8个区块（3x3范围）从迷雾状态变为"已探索"。
  - 已探索区块 **永久可见**（即使玩家离开该区域后仍可在小地图或大地图UI查看该区块的静态信息，但动态信息如其他玩家位置/资源节点存量需重新进入才能实时更新）。
  - 探索进度持久化在服务器（Character 表增加 `exploredChunks: chunkId[]` 或独立的 ExploredChunk 表记录 `characterId + chunkId`）。
- **视觉表现**：
  - 未探索区块：纯黑迷雾覆盖，或半透明灰色蒙版 + "?" 图标，Tilemap 不加载该区块贴图。
  - 已探索但不在当前可视范围内的区块：低饱和度/去色处理（灰白色调），表示"记忆中的地图"，不显示动态实体（其他玩家/资源节点冷却状态）。
  - 当前可视范围内的区块（玩家周围 5x5 或动态调整）：正常彩色渲染，实时同步动态数据。

**前端实现要点**
- `WorldScene` 增加迷雾遮罩层（Phaser Graphics 或 RenderTexture），根据 `exploredChunks` 状态动态更新遮罩。
- 地图加载策略调整：仅加载"已探索区块"的静态 Tilemap 数据（非迷雾），"当前可视范围"区块额外加载动态实体（玩家/资源节点）。
- 小地图 UI（minimap）显示已探索区域的缩略图，未探索部分显示为迷雾。

**后端调整**
- `/map/:continent/chunks` 接口增加参数 `exploredOnly=true`，返回该玩家已探索的区块列表（避免客户端请求全大陆数据）。
- WebSocket 事件 `player:move` 触发时，服务器检测玩家进入的新区块，若为首次探索则广播 `map:explore` 事件（携带新解锁的区块ID列表），客户端更新迷雾状态。

**与其他系统的关联**
- **传送门系统**：传送到未探索城镇时，该城镇所在区块及周围区块自动标记为已探索（传送不应受迷雾阻碍）。
- **好友系统**：传送到好友所在区块时，同样自动探索该区块（见 2.7）。
- **交通工具系统**：飞行器可能需要特殊视野机制（如临时扩大探索范围或显示鸟瞰视角），见 2.8。

### 2.7 好友与社交系统

**设计目标**：支持玩家之间发现、添加好友、维护社交关系，通过好友传送、聊天等功能增强社交粘性。

**玩家发现机制**
- **发现条件**：
  - 两名玩家进入同一区块或相邻区块（即相距≤1区块范围）时，彼此可见对方的角色精灵（Phaser Sprite）。
  - 可见范围外的玩家不渲染，避免广播风暴（已通过区块房间分区广播实现，见 3.2）。
- **互动入口**：
  - 点击/悬停其他玩家的角色，弹出简易信息卡片（昵称、等级/称号、在线状态）。
  - 信息卡片提供按钮：「发送好友请求」「查看主页（若未来有玩家主页功能）」。

**玩家信箱（Mailbox）**
- 用于接收和管理各类消息：好友申请、系统通知、好友聊天（若未来支持离线消息）。
- UI 位置：游戏主界面右上角常驻图标（信封/邮箱图标），有未读消息时显示红点数字。
- 信箱分类：
  - **好友申请**：待处理的好友请求列表（发送者昵称、时间、接受/拒绝按钮）。
  - **系统消息**：官方公告、活动通知、违规警告等（后续扩展）。
  - **好友消息**：好友聊天记录（若实现离线聊天功能，Phase 4 可选）。

**好友申请流程**
1. 玩家 A 在地图上发现玩家 B，点击 B 的角色 → 信息卡片 → 「发送好友请求」。
2. 客户端发送 WebSocket 事件 `friend:sendRequest`（目标 characterId）。
3. 服务器校验（双方未达好友上限、未重复申请、未被拉黑）后，插入 `FriendRequest` 记录（status: pending），实时推送通知到玩家 B（若在线则弹出提示，若离线则存入信箱待登录后查看）。
4. 玩家 B 打开信箱 → 好友申请列表 → 点击「接受」或「拒绝」。
5. 若接受：服务器插入 `Friendship` 记录（双向，A-B 和 B-A 各一条或单条记录含双向标志），更新 `FriendRequest.status = accepted`，双方好友列表实时更新。
6. 若拒绝：更新 `FriendRequest.status = rejected`，仅记录不生成好友关系。

**好友功能**
- **好友列表**（HUD 新增 FriendListPanel.vue）：
  - 显示所有好友（昵称、在线状态、所在大洲/区块名称）。
  - 在线状态实时同步（通过 Redis + WebSocket 推送，类似"谁在线"机制）。
  - 排序：在线优先，或按最近互动时间排序。
- **传送到好友**：
  - 点击好友列表中的在线好友 → 「传送到TA的位置」按钮。
  - 校验条件：
    - 冷却时间（如 5-10 分钟，避免频繁传送）。
    - 资源消耗（可选，如消耗少量矿物或货币，避免完全免费削弱探索价值）。
    - 好友所在区块非私密区域（若未来有私人副本/房间隐私设置，需拒绝传送）。
  - 传送成功后，玩家移动到好友所在区块的随机空地位置（避免精确重叠），该区块及周围自动标记为已探索。
**好友聊天与飞鸽传信系统**
- **私聊频道（同区块 / 好友在线）**：
  - 点击好友 → 「发送消息」打开私聊窗口（ChatPanel 复用或新增 PrivateChatPanel）。
  - **同区块即时聊天**：若双方在同一区块或相邻区块（物理距离近），消息即时送达（WebSocket 实时转发，零延迟）。
  - **跨区块好友在线聊天**：若好友在线但不在附近区块，消息依然即时送达（通过 Socket.io 的好友私聊房间转发）。
- **飞鸽传信（跨区块 / 离线消息 / 非好友）**：
  - **适用场景**：
    1. 给不在线的好友发消息（离线留言）。
    2. 跨大洲、跨区块向远距离玩家发送消息（即使对方在线，若距离过远也可选择飞鸽传信增加沉浸感，Phase 4 后可选）。
    3. 向非好友玩家发送消息（如交易邀请、组队邀请，需对方同意接收陌生消息）。
  - **传信机制**：
    - 发送方在信箱或好友列表中选择「飞鸽传信」，撰写消息（字数限制，如 200 字，避免滥用）。
    - 消息进入"传递中"状态，根据距离与交通渠道计算送达延迟：
      | 条件 | 延迟时间（建议） |
      |---|---|
      | 同区块 / 相邻区块 | 即时（0 延迟） |
      | 同大洲内跨区块（无交通渠道） | 5-15 分钟（模拟信鸽飞行） |
      | 同大洲内跨区块（有交通渠道*） | 2-5 分钟 |
      | 跨大洲（无交通渠道） | 15-30 分钟 |
      | 跨大洲（有交通渠道） | 5-10 分钟 |
      - *交通渠道定义：双方所在区块之间存在已建立的传送门连接（通过城镇传送门解锁链路），或双方所在城镇有 NPC 快速航线（Phase 4.5 后扩展）。
    - 消息送达后，接收方信箱收到通知（红点提示），打开信箱查看消息内容。
    - 若接收方在线，额外弹出即时提示："您收到一封来自 [玩家昵称] 的飞鸽传信"。
  - **回信机制**：接收方可直接回复飞鸽传信（同样经历延迟），或选择"传送到发件人位置"（需满足好友传送条件或消耗额外资源）进行面对面交流。
- **消息历史记录**：
  - 好友私聊与飞鸽传信的历史记录统一存储在信箱"好友消息"分类下。
  - 服务器短期缓存（如最近 100 条），长期存储可选（涉及存储成本）。
- **防滥用机制**：
  - 飞鸽传信有冷却时间（如每 5 分钟最多发送 3 条，避免刷屏）。
  - 玩家可在设置中开启"拒绝陌生人飞鸽传信"（只接收好友消息）。
  - 举报系统：接收方可举报恶意/骚扰消息，系统封禁发送者的飞鸽传信权限。

**数据模型**
- **Friendship**：`id, characterId1, characterId2, createdAt, lastInteractAt`
  - 双向关系，可存为单条记录（characterId1 < characterId2 保证唯一性）或双向各存一条（查询更直观）。
- **FriendRequest**：`id, fromCharacterId, toCharacterId, status(pending/accepted/rejected), createdAt, respondedAt`
  - 用于追溯申请历史，防止短时间内重复申请。
- **Mailbox**（可选，若信箱仅为前端聚合展示则无需独立表）：若需离线消息持久化则新增 `Message` 表：`id, receiverId, type(friend_request/system/chat), content(JSON), isRead, createdAt`。

**权限与隐私**
- 玩家可在设置中开启「拒绝陌生人好友请求」（所有请求自动拒绝）或「隐身模式」（在线但好友列表显示为离线，且无法被发现）。
- 拉黑功能（Phase 5 或后续）：被拉黑玩家无法发送好友请求、无法看见对方在线状态。

### 2.8 交通工具系统

**设计目标**：提供多样化的移动方式，通过制作/升级交通工具获得速度加成与跨地形能力，丰富资源消耗的长线目标，支持跨大洲旅行的沉浸式体验。

**交通工具等级与类型**
| 等级 | 类型 | 移动速度 | 跨地形能力 | 制作成本 | 载客能力 |
|---|---|---|---|---|---|
| 0 | 徒步（默认） | 100% | 陆地 | 无 | 单人 |
| 1 | 马匹/马车 | 150% | 陆地 | 木头x50 + 石头x20 | 单人或双人（马车） |
| 2 | 船只（小帆船） | 120%（陆地）/ 180%（水面） | 陆地 + 海洋 | 木头x100 + 矿物x30 | 2-4人 |
| 3 | 飞行器（热气球/飞艇） | 200% | 全地形（可跨山/海） | 木头x150 + 矿物x80 + 特殊材料（如"魔法水晶"） | 4-6人 |

**制作机制**
- **制作入口**：背包/建造菜单新增「交通工具」分类（VehicleCraftPanel.vue）。
- **制作流程**：
  1. 选择交通工具模板（马匹/船只/飞行器），查看所需资源清单。
  2. 校验背包资源是否足够，扣除资源后生成交通工具实体（Vehicle 表记录 `characterId + vehicleType + durability（耐久度，可选）`）。
  3. 交通工具出现在玩家的"载具栏"（类似背包但独立分类），玩家可"装备"（即切换为当前使用的交通工具）。
- **耐久度机制（可选，Phase 5 后考虑）**：交通工具使用一定距离后耐久度降低，需消耗资源修理或重新制作，避免一次制作永久使用导致资源体系后期无消耗。

**功能差异**
- **移动速度**：装备交通工具后，角色的移动速度（Phaser Sprite velocity）按对应倍率提升。前端 WorldScene 监听装备事件，动态调整移动参数。
- **跨地形能力**：
  - 徒步/马匹：仅能在陆地区块移动，进入"海洋区块"（若四大洲间有海洋分隔）时被阻挡（弹出提示"需要船只才能通行"）。
  - 船只：可在陆地与海洋区块自由切换，但速度在陆地上较慢（模拟船只在陆地拖行），在海洋上速度提升。
  - 飞行器：忽略地形限制（山脉/海洋/河流均可直线穿越），但制作成本高且可能需要特殊燃料（如"魔法水晶"周期性消耗，避免过度破坏探索平衡）。
- **载客能力（多人交通工具）**：
  - 马车/船只/飞行器可邀请其他玩家"乘坐"（需双方同意）。
  - 乘客的移动控制权交给载具主人（类似"跟随模式"），乘客可随时下车。
  - 多人共乘时移动速度可能略微降低（如 -5% per 额外乘客），平衡多人便利性。

**跨洲旅行设计**
- **大洲间地理结构**：四大洲之间由"海洋区块"分隔（如东洲与南洲之间有5-10个连续的海洋区块），徒步/马匹无法直接穿越。
- **跨洲方式**：
  1. **船只**：玩家制作船只后，可驾驶船只穿越海洋区块，自由往返各大洲（探索感强，但耗时较长）。
  2. **传送门（城镇）**：已形成城镇的区域拥有传送门，玩家解锁目标城镇后可跨洲传送（快速但需先探索到目标城镇或通过好友传送）。
  3. **港口城镇传送**：在沿海城镇（如东洲的"渔村镇"、西洲的"矿港镇"）可能有NPC或特殊传送门提供"跨洲航线"（消耗货币/资源，类似快速旅行），作为船只与传送门之间的折衷方案（Phase 4 后考虑）。
- **海洋区块内容**：海洋区块并非纯空旷，可分布：
  - 稀有资源节点（如"珊瑚""深海矿物"，船只可停靠采集）。
  - 小岛区块（景观或隐藏聊天室，鼓励探索）。
  - 动态天气/事件（如暴风雨减速、海盗NPC，后续扩展）。

**前端渲染**
- 装备交通工具后，角色 Sprite 替换为"角色+载具"组合精灵（如骑马状态、坐在马车上、船只上的角色小人），或载具作为独立 Sprite 跟随角色。
- 飞行器可能需要额外的 Z 轴高度视觉表现（阴影/高度偏移），与地面实体区分。

**后端逻辑**
- Vehicle 表：`id, characterId, vehicleType, durability, equippedAt, createdAt`
- 移动校验增强：服务器校验 `player:move` 事件时，检查目标区块地形类型（陆地/海洋/山地）与玩家当前装备的交通工具是否匹配，不匹配则拒绝移动并返回错误（防止客户端作弊直接穿海）。

### 2.9 团队系统

**设计目标**：允许玩家组建团队，共享地块上限与资源，协作建设更大规模的城镇或聊天室集群，增强合作玩法与社交深度。

**组队机制**
- **创建团队**：
  - 玩家可在游戏主界面选择「创建团队」，输入团队名称（唯一性校验），消耗一定资源或货币（可选，Phase 3 决策），创建团队实体（Team 表，创建者自动成为队长 leader）。
  - 团队名称支持搜索，便于其他玩家查找加入。
- **邀请/申请加入**：
  1. **队长邀请**：队长可通过玩家 ID/昵称搜索或在地图上点击其他玩家，发送「邀请加入团队」请求（TeamInvitation 表，status: pending）。
  2. **玩家申请**：玩家可搜索团队名称，向目标团队发送「申请加入」请求（TeamApplication 表，status: pending），队长审批。
  3. 邀请/申请通过后，玩家加入团队（TeamMember 表插入记录，role: member），实时更新团队成员列表。
- **退出/踢出团队**：
  - 成员可主动退出团队（TeamMember 记录删除，团队地块上限重新计算）。
  - 队长可踢出成员（需确认对话框，防止误操作）。
  - 队长退出团队时需转让队长权限给其他成员，或解散团队（所有团队地块的所有权按贡献度分配给各成员，或统一变为无主地块，Phase 3 需明确规则）。

**团队地块上限与共享机制**
- **团队地块上限**（随团队人数递增）：
  | 团队人数 | 地块上限 |
  |---|---|
  | 1 人（未组队个人） | 10 块 |
  | 2 人团队 | 15 块 |
  | 3 人团队 | 20 块 |
  | 4 人团队 | 25 块 |
  | 5 人团队 | 30 块 |
  | 6 人及以上 | 每增加 1 人 +4 块（如 6 人 34 块，10 人 50 块） |
  - 数值为建议，Phase 3 需根据地图规模与经济平衡调优。
- **所有权归属**：
  - 团队成员在任一团队拥有的地块上建造聊天室后，该地块的 `ownerId` 可设为团队 ID（`teamId`）而非个人 ID，或在 MapChunk 表增加 `teamId` 字段（`ownerId` 保留建造者个人 ID，便于追溯贡献）。
  - 团队地块计入团队总上限，不计入个人上限（即加入团队后，个人地块 + 团队地块共享同一池）。
- **成员权限**：
  - **队长（leader）**：完全权限（邀请/踢人/解散团队/设置团队地块公开状态/转让队长）。
  - **成员（member）**：
    - 可以在团队拥有的任一地块上建造聊天室（消耗各自背包资源，Phase 3 可选引入"团队资源池"，所有成员共享资源）。
    - 可以进入团队地块上的聊天室并拥有成员权限（可发言/使用听歌看视频，但不能删除他人建造的房间或踢出其他团队成员，除非房间拥有者授权）。
    - 不能修改团队地块的公开状态（仅队长或地块建造者可设置）。

**团队资源池（可选，Phase 4 后扩展）**
- 团队可拥有共享资源仓库（TeamResourcePool 表），成员可将个人背包资源存入/取出。
- 团队建造时优先消耗团队资源池，不足时扣除个人背包。
- 避免资源分配纠纷，需设计"贡献度"机制（记录每个成员存入的资源量，退出团队时按贡献度分配剩余资源）。

**团队聊天频道**
- 团队拥有独立的聊天频道（TeamChatChannel），所有在线成员均可发言与接收消息（类似公会频道）。
- UI 位置：HUD 新增 TeamChatPanel.vue，或在 ChatPanel 中增加频道切换（世界/团队/私聊）。

**团队UI**
- HUD 新增 TeamPanel.vue：
  - 显示团队信息（名称、队长、成员列表、地块占用情况 [X/30]）。
  - 成员列表：昵称、在线状态、贡献度（若实现）、踢出按钮（队长可见）。
  - 邀请/申请入口、退出团队按钮。

**数据模型**
- **Team**：`id, name, leaderId(characterId), createdAt, updatedAt`
- **TeamMember**：`id, teamId, characterId, role(leader/member), joinedAt, contribution(可选贡献度)`
- **TeamInvitation**（可选，若需追溯邀请历史）：`id, teamId, fromCharacterId, toCharacterId, status(pending/accepted/rejected), createdAt`
- **TeamApplication**（可选）：`id, teamId, characterId, status(pending/accepted/rejected), createdAt`
- **MapChunk 扩展**：增加 `teamId` 字段（可为 NULL，NULL 表示个人地块或无主地块）

## 3. 技术架构设计

### 3.1 前端架构（Vue + Phaser）

**分层原则**：Phaser 只负责"游戏世界"渲染（地图、角色、动画、区块加载/卸载），所有表单类/面板类 UI（登录、背包、建造菜单、聊天面板、设置）用 Vue 组件实现，两者通过一个轻量事件总线（EventBus，可用 `mitt` 或简单的自定义 EventEmitter）通信，避免 Phaser Scene 内直接操作 DOM，也避免 Vue 组件直接持有 Phaser 内部对象引用。

**Vue 组件结构（建议）**
```
src/
  main.ts
  App.vue                      # 根组件：根据登录态切换 Auth / Game 布局
  views/
    AuthView.vue                # 登录/注册/创角流程
    GameView.vue                # 承载 PhaserCanvas + 各类悬浮面板
  components/
    game/
      PhaserCanvas.vue          # 挂载 Phaser.Game 实例，负责生命周期管理
      HUD/
        InventoryPanel.vue      # 背包
        BuildMenu.vue           # 建造菜单
        ChatPanel.vue           # 聊天室内文字聊天面板
        MediaSyncPanel.vue      # 听歌/看视频控制面板
```

**状态管理**：引入 Pinia 作为跨 Vue 组件的状态管理方案（当前脚手架仅有 `vue`，需新增 `pinia` 依赖）。Phaser 内部状态（区块加载、精灵位置等）保留在 Phaser Scene 内部，仅将"需要 UI 展示"的数据（背包、房间信息、在线成员）通过 EventBus 同步到 Pinia store。

**Phaser 场景设计**
- `BootScene`：初始化配置、加载 loading 资源。
- `PreloadScene`：加载图集、Tilemap、音效等美术资源。
- `WorldScene`：主世界场景，负责地图区块的动态加载/卸载（基于玩家可视范围向服务器请求区块数据）、角色移动同步、资源节点渲染与交互、建造/传送门的触发入口。**增加迷雾遮罩层（Graphics/RenderTexture）根据探索状态动态更新（Phase 2）**。**渲染其他玩家 Sprite，支持点击弹出信息卡片（Phase 3）**。**根据装备的交通工具动态调整角色移动速度与 Sprite 外观（Phase 3/4）**。
- `RoomScene`（可选）：如果聊天室内部是独立像素场景（而非纯 UI 面板），则进入房间时切换到此场景，负责房间内装饰摆放的可视化。

### 3.2 后端架构（Node.js）

**技术选型**
- 运行时：Node.js + TypeScript
- 实时通信：`Socket.io`（比原生 `ws` 更省心地处理房间/命名空间/重连，契合本游戏"区块房间+聊天室房间"的多房间模型）
- REST API：Express 或 Fastify，用于登录注册、非实时的资源查询类接口
- 数据库：PostgreSQL（用户、角色、聊天室、城镇等结构化关系数据）+ Redis（在线状态、区块内玩家位置等高频读写的临时状态、消息发布订阅）

**服务分层**
```
Gateway 层 (Socket.io)
  - 连接鉴权（校验 JWT）
  - 房间管理：按"区块"分房间（同区块玩家收到彼此的位置同步），按"聊天室ID"分房间（聊天/听歌/看视频广播）
  - 消息路由：收到客户端事件 -> 转发给对应 Game Logic 处理

REST API 层 (Express)
  - /auth/register /auth/login /auth/refresh
  - /character (创建/查询角色)
  - /spawn-point/select (出生点选择：无主地块/公开地块池查询与分配，Phase 1)
  - /map/:continent/:chunkId (拉取区块静态数据，供客户端首次进入时加载)
  - /map/explored (查询玩家已探索区块列表，Phase 2)
  - /chunks/owned (查询玩家拥有的地块列表，Phase 2)
  - /chunks/:chunkId/public (设置地块公开状态，Phase 2)
  - /friends (好友列表/申请/接受/拒绝，Phase 3)
  - /mailbox (信箱消息查询，Phase 3)
  - /mailbox/pigeon (发送飞鸽传信，Phase 3)
  - /vehicles (交通工具列表/制作，Phase 3/4)
  - /teams (团队创建/查询/邀请/申请，Phase 3)
  - /teams/:teamId/members (团队成员管理，Phase 3)

Game Logic 层
  - MovementService：校验/广播玩家移动，**集成交通工具速度加成与地形校验（Phase 3/4）**
  - ResourceService：采集校验、资源冷却刷新（定时任务）
  - BuildService：建造校验（资源扣减、区块类型变更、**地块所有权获得 Phase 2**）
  - TownService：城镇密度检测、城镇信息维护
  - PortalService：传送校验（是否解锁、冷却）
  - RoomService：聊天室内文字/听歌/看视频状态广播、装饰数据变更
  - PluginService：插件市场后台（上传/审核/分发）
  - PluginSessionManager：管理房间内插件会话（创建/状态同步/销毁）
  - PluginSandbox：服务端插件脚本沙箱执行环境（VM2 / Worker 进程隔离）
  - ExplorationService：探索状态管理，**处理 player:move 触发的区块探索逻辑（Phase 2）**
  - FriendService：好友申请/接受/拒绝、好友列表查询、**好友传送校验（Phase 3）**
  - VehicleService：交通工具制作校验、装备切换、**地形匹配校验（Phase 3/4）**
  - ChunkOwnershipService：**地块所有权管理（获得/放弃/公开设置/上限校验 Phase 2）**
  - TeamService：**团队创建/邀请/申请/成员管理、团队地块上限计算（Phase 3）**
  - PigeonMailService：**飞鸽传信延迟计算与消息队列处理（Phase 3）**

持久化层
  - PostgreSQL：User / Character / MapChunk / ResourceNode(定义) / ChatRoom / Town / Portal / Plugin / RoomPlugin / PluginSession / ExploredChunk / Friendship / FriendRequest / Vehicle / Mailbox(可选) / **Team / TeamMember / TeamInvitation / TeamApplication / PigeonMessage**
  - Redis：在线玩家位置缓存、区块房间订阅、资源节点冷却计时器、插件会话状态（热数据）、好友在线状态（Phase 3）、**飞鸽传信延迟队列（Phase 3）、出生点池缓存（无主地块/公开地块列表 Phase 1）**
```

**分区广播（避免全服广播）**：世界地图按大洲/区块分成多个 Socket.io 房间，玩家的移动、采集等事件只广播给同区块（或相邻区块）内的其他玩家，聊天室内的聊天/听歌/看视频消息只广播给对应聊天室房间内成员，从架构上避免"全服玩家共享一个大房间"导致的广播风暴。

### 3.3 数据模型设计（核心实体，字段为建议，非最终DDL）

**基础系统**
- **User**：`id, username, email, passwordHash, createdAt`
- **Character**：`id, userId, nickname, appearance(JSON), continent, currentChunkId, position{x,y}, spawnMethod(random_unowned/random_public/invited), createdAt`

**地图与资源**
- **MapChunk**：`id, continent, chunkX, chunkY, type(资源/景观/空地/聊天室/海洋), meta(JSON), ownerId(characterId或NULL), teamId(可选，NULL表示个人或无主), isPublic(boolean，默认false)`
- **ResourceNode**：`id, chunkId, resourceType(木头/石头/矿物), position{x,y}, respawnAt, isDepleted`
- **InventoryItem**：`id, characterId, itemType, quantity`

**聊天室与城镇**
- **ChatRoom**：`id, chunkId, ownerId, name, template, level, decorations(JSON), createdAt`
- **RoomMember**：`id, roomId, characterId, role(房主/成员/访客), joinedAt`
- **Town**：`id, continent, name, level, centerChunkId, portalId`
- **Portal**：`id, townId, unlockedBy(characterId[]), cooldownSeconds`
- **ChatMessage**（短期缓存，非必须长期落库）：`id, roomId, characterId, content, sentAt`

**插件系统**
- **Plugin**（插件市场）：`id, name, version, author, manifest(JSON), packageUrl, status(审核中/已上架/下架), createdAt, updatedAt`
- **RoomPlugin**（房间已安装插件）：`id, roomId, pluginId, installedBy(characterId), installedAt, config(JSON)`
- **PluginSession**（插件会话）：`id, roomId, pluginId, participants(characterId[]), state(JSON), startedAt, endedAt`

**探索系统（Phase 2）**
- **ExploredChunk**：`id, characterId, chunkId, exploredAt`
  - 或在 Character 表增加 `exploredChunks: chunkId[]` JSON字段（小规模数据可行，大规模需独立表+索引优化）

**好友系统（Phase 3）**
- **Friendship**：`id, characterId1, characterId2, createdAt, lastInteractAt`
  - 建议双向存储（id1 < id2 保证唯一），或各存一条便于单向查询
- **FriendRequest**：`id, fromCharacterId, toCharacterId, status(pending/accepted/rejected), message(可选申请留言), createdAt, respondedAt`
- **Mailbox**（可选，若仅前端聚合展示则无需独立表）：
  - 若需持久化离线消息，新增 **Message** 表：`id, receiverId, type(friend_request/system/chat), senderId(可选), content(JSON), isRead, createdAt`
- **PigeonMessage**（飞鸽传信）：`id, senderId, receiverId, content, distance(区块距离), hasTrafficChannel(boolean), calculatedDelay(秒), sentAt, deliveredAt(NULL表示传递中)`

**交通工具系统（Phase 3/4）**
- **Vehicle**：`id, characterId, vehicleType(horse/cart/ship/airship), durability(耐久度), isEquipped(boolean), createdAt`
  - 或 Character 表增加 `equippedVehicleId` 外键指向当前装备的交通工具

**团队系统（Phase 3）**
- **Team**：`id, name, leaderId(characterId), createdAt, updatedAt`
- **TeamMember**：`id, teamId, characterId, role(leader/member), joinedAt, contribution(可选贡献度，JSON或独立字段)`
- **TeamInvitation**（可选）：`id, teamId, fromCharacterId, toCharacterId, status(pending/accepted/rejected), createdAt`
- **TeamApplication**（可选）：`id, teamId, characterId, message(可选申请留言), status(pending/accepted/rejected), createdAt`

**关系简述**：`User 1—1 Character`，`Character N—1 MapChunk(currentChunkId)`，`Character N—N MapChunk(通过 ExploredChunk)`，`Character 1—N MapChunk(通过 ownerId，地块所有权)`，`MapChunk 1—0/1 ResourceNode`，`MapChunk 1—0/1 ChatRoom`，`ChatRoom N—1 Town`，`Town 1—1 Portal`，`ChatRoom N—N Plugin(通过 RoomPlugin)`，`PluginSession N—1 ChatRoom + Plugin`，`Character N—N Character(通过 Friendship)`，`Character 1—N Vehicle`，`Character N—1 Team(通过 TeamMember)`，`Team 1—N MapChunk(通过 teamId)`。

| **Phase 2：资源采集 + 建造系统 + 视野系统 + 地块所有权** | 玩家可采集资源并建造聊天室，**建造后获得地块所有权**，地图探索揭开迷雾，可管理拥有的地块 | 资源节点刷新逻辑；采集交互与服务器校验；建造菜单UI；空地区块→聊天室区块的状态流转；**建造时自动获得地块所有权（ChunkOwnershipService）、地块管理面板（ChunkOwnershipPanel：查看拥有地块/公开设置/放弃地块）、个人地块上限校验（默认10块）**；**RoomScene 内预留 PluginContainer 插槽（UI层）与 Phaser Container（场景层）**；**迷雾遮罩层实现（WorldScene Graphics）、ExploredChunk 表与探索逻辑（ExplorationService）、已探索区块持久化与加载** |
| **Phase 3：城镇系统 + 传送门 + 好友系统 + 团队系统 + 交通工具基础 + 飞鸽传信** | 聊天室聚集形成城镇，城镇间可传送；玩家可添加好友、查看在线状态、传送到好友、通过飞鸽传信跨区块沟通；玩家可组建团队，共享地块上限；制作基础交通工具（马匹/马车） | 城镇密度检测/命名；传送门UI与解锁校验；四大洲地图内容补全（美术主题差异化）；**好友申请/列表/聊天（FriendService + Friendship/FriendRequest 表）、信箱UI（MailboxPanel）、玩家发现与信息卡片（PlayerInfoCard）、好友在线状态同步（Redis + WebSocket）、好友传送功能（冷却/资源消耗校验）**；**飞鸽传信系统（PigeonMailService：延迟计算[距离+交通渠道]、消息队列处理、送达通知）**；**团队创建/邀请/申请/成员管理（TeamService + Team/TeamMember 表）、团队面板（TeamPanel）、团队聊天频道（TeamChatPanel）、团队地块上限计算（2人15块、3人20块等）、团队成员在团队地块建造权限**；**交通工具制作系统（VehicleCraftPanel + Vehicle 表）、马匹/马车速度加成（MovementService 集成）、交通工具 Sprite 渲染** |
| **Phase 4：聊天室社交功能** | 聊天室内的核心社交玩法上线 | 房间文字聊天；一起听歌/看视频的同步播放；房间装饰摆放系统；房间权限（房主/成员/访客）；**（后期）SDK核心API接口定义（RoomAPI/PlayerAPI/UIAPI/NetworkAPI），发布 @reifuu-chat/plugin-sdk v0.1（alpha版，供内部测试插件开发）** |
| **Phase 4.5（可选）：交通工具高级功能** | 船只与飞行器，支持跨洲旅行 | **船只制作与海洋区块穿越逻辑（MapChunk 新增海洋类型、MovementService 地形校验）、飞行器制作与全地形能力、多人载具（载客逻辑）、海洋区块资源节点/小岛内容、大洲间地理结构调整（海洋分隔）** |
| **Phase 5：打磨与上线准备** | 稳定性、体验与规模化准备 | 性能优化（区块动态加载卸载、Socket.io 房间压测、迷雾系统渲染优化）；反作弊校验补强（交通工具地形作弊检测、好友传送滥用限制）；数值平衡（资源刷新/建造消耗/交通工具成本）调优；部署与监控（日志、错误上报）；**插件市场UI上线（PluginMarketPanel）、插件沙箱机制完善、审核流程落地、SDK文档与示例插件发布** |
| **Phase 6（可选）：插件生态启动** | 开放插件开发，启动社区生态 | SDK正式版发布（@reifuu-chat/plugin-sdk v1.0）；插件开发文档/教程/示例（官方示例插件：斗地主、狼人杀、投票器等）；插件市场开放社区上传；开发者激励计划（分成/奖金） |

**阶段间依赖说明**：
- Phase 1 是后续所有玩法的地基（地图+移动+同步），**出生点选择机制影响新手体验与地块分布（无主地块/公开地块池需在 Phase 0 数据模型中预留字段）**，必须先跑通。
- Phase 2 与 Phase 3 存在强先后关系（先有聊天室才有城镇），**视野系统与地块所有权在 Phase 2 落地，影响地图加载逻辑（前端迷雾渲染+后端探索状态管理+地块所有权获得/管理）**。
- Phase 3 新增好友系统、团队系统、飞鸽传信与交通工具基础（马匹/马车），**好友传送、团队地块上限、飞鸽传信延迟计算均需 Phase 2 的地图系统与地块所有权稳定后实施**。
- Phase 4 可与 Phase 3 部分并行（社交功能不强依赖城镇系统，但依赖 Phase 2 的聊天室实体已存在）。
- **Phase 4.5 为可选高级交通工具阶段，建议在 Phase 5 之前完成（若跨洲旅行为核心体验）或后置到 Phase 6 后（若优先插件生态）**。
- **插件扩展架构从 Phase 0 即开始预留接口（数据模型、前端容器），Phase 4 后期开始落地 SDK，Phase 5 完善市场与沙箱，Phase 6 正式开放生态**。

## 5. 待决策/风险项（后续需与团队对齐）

1. **听歌/看视频的版权与技术方案**：需明确是否接入第三方平台embed（如 YouTube/网易云 API）还是自建曲库，涉及合规与开发成本。
2. **区块尺寸与可视范围的性能验证**：32x32 tile + 分区房间广播的方案需在 Phase 1 末做实际压测，确认多人同区块时的同步延迟可接受。
3. **城镇自动生成 vs 玩家主动建镇**：两种机制的取舍影响后续数值设计与新手引导，建议 Phase 3 前与产品/主美对齐。
4. **好友系统/PVP等扩展玩法**：当前文档未纳入，若后续需要应作为独立迭代规划，不影响本阶段架构（数据模型已预留 Character 独立实体，扩展成本较低）。
5. **插件沙箱执行环境技术选型**：前端可用 iframe + postMessage 或受限 eval（去掉危险全局变量），服务端可用 VM2（已停止维护，需评估安全性）、isolated-vm（性能更好但API复杂）或独立 Worker 进程（隔离性最强但通信开销大），Phase 4 前需做技术选型验证。
6. **插件市场审核机制与人力成本**：纯机器审核（代码静态扫描+沙箱试运行）可过滤明显恶意插件，但无法检测内容质量/玩法抄袭/诱导充值等问题，是否需配置人工审核流程？需产品/运营介入讨论。
7. **插件开发者激励与分成模型**：SDK开放后如何吸引社区开发者？考虑插件内道具付费分成、开发者奖金池、官方采购优质插件等机制，Phase 6 前需定义商业模式。
8. **迷雾系统的探索范围平衡**：初始 5x5 区块、移动揭开 3x3 的数值需在 Phase 2 实装后根据实际地图规模与玩家反馈调优，避免过小导致频繁迷雾（体验割裂）或过大削弱探索感。
9. **好友传送的冷却与消耗设计**：需在 Phase 3 前明确冷却时间（建议 5-15 分钟）与资源消耗（可选，如少量矿物），避免好友传送完全取代探索/交通工具，削弱其他系统价值。
10. **交通工具耐久度机制是否引入**：耐久度可创造资源长线消耗目标，但也增加玩家维护负担；建议 Phase 4.5 实装船只/飞行器时根据经济系统整体健康度决策，Phase 3 的马匹/马车可先不加耐久度（简化MVP体验）。
11. **跨洲海洋区块的内容密度**：海洋区块若过于空旷，船只穿越将变成纯等待时间（负面体验）；需在 Phase 4.5 前规划海洋区块的稀有资源/小岛/动态事件分布密度，或提供"快速航线"（NPC港口传送）作为备选方案。
12. **出生点匹配算法的公平性与体验**：无主地块池需确保地理分布均匀（避免新玩家全部出生在偏远角落），公开地块池需避免人口过度集中（按人口密度/活跃度排序，优先推荐适度人气区块）；Phase 1 实装后需根据实际数据调优匹配权重。
13. **地块上限数值平衡**：个人默认 10 块、团队递增规则（2人15块、3人20块等）需在 Phase 2-3 实测后根据地图规模与玩家扩张速度调优，避免过低限制玩法深度或过高导致地图过早饱和。
14. **团队解散时的资源与地块分配规则**：队长解散团队或退出时，团队拥有的地块所有权如何处理（按贡献度分配给各成员？统一变为无主？转给新队长？）、团队资源池如何分配（若引入），Phase 3 前需明确规则，避免玩家纠纷。
15. **飞鸽传信延迟的游戏体验权衡**：5-30 分钟的延迟可能削弱即时沟通需求（玩家转而使用外部IM工具），但零延迟又失去"飞鸽传信"的沉浸感；建议 Phase 3 实装后通过用户反馈调整延迟数值（或提供"加急传信"消耗资源缩短延迟，兼顾沉浸与体验）。
16. **团队资源归属机制**：Phase 3 团队成员在团队地块建造时消耗个人背包资源还是团队共享资源池？若引入团队资源池，需设计贡献度追踪与退出时分配规则（Phase 4 后扩展），避免"白嫖"或资源纠纷。
